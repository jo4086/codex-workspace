# UI 템플릿 도입 검토

## 질문

> 앞으로 구체적인 UI는 templates/ui/ 이런구조를 사용해서
>
> 아예 형태와 컴포넌트 코드 자체가 있는 템플릿을 두고 내가 어떤 템플릿 쓸꺼라고하면 그걸 바로 적용하는 그런 구조로 가는게 좋을려나

## 답변

네. **여러 프로젝트에서 같은 형태와 동작을 재사용하고 싶고, 어떤 것을 쓸지 직접 지정할 생각이라면 templates/ui/가 잘 맞습니다.** 예를 들어 이미지 갤러리의 배치·확대·닫기 동작을 매번 지침으로 설명하는 대신, 한 번 구현하고 검증한 컴포넌트를 재사용할 수 있습니다. 일반 UI 작업에서는 그 코드를 읽을 필요도 없습니다.

처음에는 실제로 재사용할 컴포넌트 하나로 시작하는 게 좋겠습니다.

```text
templates/ui/
└── image-lightbox/
    ├── README.md
    ├── ImageLightbox.tsx
    └── image-lightbox.css
```

`README.md`는 **어떤 모양인지, 어떤 props를 받는지, 어떤 의존성이 필요한지**만 짧게 담으면 됩니다. 형태가 중요하면 미리보기 한 장을 붙이고, 키보드나 포커스 동작이 중요한 템플릿은 그 동작을 코드와 함께 검증해 두는 편이 좋습니다.

사용 방식도 간단합니다. **“image-lightbox 템플릿을 적용해줘”**라고 하면 그 폴더만 열고, 템플릿의 배치와 동작을 기준으로 대상 프로젝트의 데이터·토큰·import 경로를 연결합니다. 그냥 “이미지 확대 기능을 만들어줘”라고 하면 기존 프로젝트와 요청을 보고 자유롭게 구현합니다. 이렇게 하면 템플릿이 하나씩 늘어도 평소 UI 작업의 지침량은 늘지 않습니다.

이 저장소에서는 **템플릿을 어디서 찾을지**만 미리 정해 두면 됩니다. 지금 동기화 스크립트는 `skills/<이름>/`을 복사하므로, 저장소 루트의 `templates/ui/`는 설치된 스킬에 포함되지 않습니다. 우선은 **루트 `templates/ui/`를 원본으로 두고, 이름을 지정했을 때만 그 원본에서 가져오는 방식**을 권합니다. 이 정도라면 새 스킬이나 전체 템플릿 목록을 매번 읽히는 절차까지 만들 필요는 없습니다.
